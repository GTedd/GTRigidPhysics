# 开发流程

> 这份文档回答一个问题：**下一件事该怎么做，才能让项目长期不塌。**
>
> 它不讲代码怎么写（那是[贡献指南](contributing.md)），也不讲版本怎么发（那是[发布流程](release.md)），
> 更不讲 Minecraft 升级怎么跟（那是[版本适配手册](version-migration.md)）。
> 它讲的是这三者之间的那一层：**一次改动从想法到落地要经过哪些关卡，
> 以及哪些关卡是不能绕的。**

---

## 1. 为什么需要一份流程文档

这个项目有两个特征，任何一个单独出现都不算稀奇，凑在一起就很危险：

**它依赖一整条高速变动的外部栈。** 下面是实测的发布节奏：

| 依赖 | 近期节奏 | 含义 |
|---|---|---|
| ~~`jolt-jni`~~ | 2026-04 到 2026-07 发了 **8 个版本**，主版本号从 4 跳到 6 | 四个月两次 major。**这正是换成自研引擎的动机之一** —— 现在这一行已经不存在了 |
| Minecraft | 26.2 正式版 2026-06-16，26.3 快照**每周一发** | 渲染管线每个版本都在改 |
| `packetevents` | 约每月一个小版本 | 协议层跟着 MC 走 |

**而它的正确性大量依赖「不可见的约定」。** native 内存的释放顺序、跨线程可见性、
display entity 的 metadata 索引、着色器的像素级编码 —— 这些东西错了不会编译失败，
也很少立刻崩，而是表现为「服务器跑几小时后 RSS 暴涨」「偶尔某场坍塌不动」
「某个玩家眼里那辆车不存在」。等到有人报 bug 时，线索早就没了。

这两条合在一起意味着：**靠「小心一点」是撑不住的，必须靠流程。**

## 2. 迭代模型：五个阶段

项目至今每一轮有效的改动都走了同一条路径。把它显式写下来，是为了下次不会漏掉某一步。

```
① 调研 ──→ ② 设计 ──→ ③ 实现 ──→ ④ 实证 ──→ ⑤ 归档
   ↑                                    │
   └──────── 实证推翻设计时回到 ① ────────┘
```

### ① 调研

**只在两种情况下可以跳过**：改动完全局限在一个已有系统内部，或者是修一个已定位的 bug。
其余情况都要先看外面。

要回答的三个问题：

- **有没有人做过？** 同类开源项目的架构、它们踩过什么坑、活跃度、许可证。
  历史结论存在 `docs/internal/prior-art-survey.md`（仓库内部材料，不进公开站点），
  新调研要追加进去而不是另起一份。
- **官方 API 支不支持？** 优先查底层库自己的源码与官方文档，**不要凭记忆**。
  依赖的 jar 里若带 sources，`unzip -p <jar> <path>` 直接读实现比查任何二手资料都准
  —— §5 里那条「批量读的条数取自 `BodyIdArray.length()` 而非缓冲容量」就是这么确认的，
  猜错了会读到数组尾部的垃圾。
- **代价是多少？** 新依赖的许可证、native 体积、平台覆盖、维护活跃度。

### ② 设计

产出是**一段可以被反驳的文字**，不是代码。至少写清楚：

- 改动要解决的具体失效场景（「100 人服上位姿广播会打满出口」，不是「优化性能」）
- 选了哪条路、放弃了哪些路、为什么
- 影响面：动了哪些模块、破不破坏现有契约、要不要改配置
- **怎么验证它真的成立**

最后一条最容易被跳过，而它恰恰决定了这次改动将来能不能被安全地重构。

### ③ 实现

按[贡献指南](contributing.md)的模块约束与注释要求写。流程上只有一条额外要求：

> **一次只推进一件事，并且每件事结束时仓库是绿的。**

不要攒一个巨大的分支。M1~M6 那一轮六项改动是逐项落地、逐项跑全量测试的 ——
其中 M2 引入了两个启动期 NPE（配置加载时机晚于服务构造），
正因为是单项验证才立刻定位到，混在六项里改完再跑就只能靠猜。

### ④ 实证

**这是本项目最不能省的一步，理由见 §4。**

### ⑤ 归档

- 面向服主/玩家的行为变化 → `docs/` 对应的系统文档
- 设计决策与实证数据 → `DESIGN.md` 追加一节（编号递增，不改旧节）
- 配置项变化 → 对应的 `.yml` 里写注释，**并说明是否支持热重载**

`DESIGN.md` 是**只追加**的：它记录的是「当时是怎么想的、测出来是什么」，
不是「现在的系统长什么样」。后者在 `docs/`。改旧节等于篡改历史，
下次有人问「为什么当初选了 A 不选 B」就再也查不到了。

## 3. 工作分级与 MVP 划定

不是所有问题都值得现在修。分级的目的是让「这次做什么、不做什么」有据可依。

| 级别 | 判据 | 处理 |
|---|---|---|
| **P0** | 架构级不一致，或会随规模增长必然失效 | 当期必修 |
| **P1** | 明确的性能/正确性缺陷，有量化依据 | 当期修，除非有 P0 抢占 |
| **P2** | 设计取向问题，或收益依赖未验证的假设 | 记录，下一轮评估 |

**判 P0 的关键不是「现在有多疼」，而是「它会不会随规模变得不可收拾」。**

举一个真实的例子：坍塌链路从第一天就有四道带宽闸门，而独立物体链路一道都没有。
单机测试时两者都很正常 —— 但独立物体是**进程级常驻**的，
坍塌是几秒钟的一次性事件。同样的疏漏，前者的累计代价随在线人数与物体数相乘，
后者不会。所以它是 P0，而不是「等出问题再说」。

### 划定 MVP 的三条规则

1. **一期只解决一类问题。** 「让 100 人服活下来」是一类；「让碎块能砸到载具」是另一类。
   混在一起会导致任何一项出问题都要回滚全部。
2. **先做低风险且能独立回归的。** 顺序是「地基 → 内部优化 → 大改动面 → 依赖前几步的」。
3. **明确写出不做什么。** 不写的话，做到一半自然会滑进去。

## 4. 实证纪律

> **不许只凭推理下性能结论，也不许只凭「测过了」下正确性结论。**

这条不是洁癖。项目里有三次教训，每一次都是「看起来显然成立」的推理被数据推翻：

### 教训一：推算值当成实测值

`DESIGN.md` §2.2 的「每碎块约 100 B」是**按协议字段推算**的，
整套预算体系（`budget.yml` 的全部限额）都建立在它之上。
文档里老老实实标了「此为推算，非抓包实测，落地需校准」——
但只要没人真去抓包，这些限额就永远是猜的。

**规则**：推算值必须在文档与配置注释里标明是推算，并写清校准方式。
任何基于它做的决策都要视为「待验证」。

### 教训二：基准测了错的东西

评估「三角网格地形」时，第一版基准在**起伏地形**上测「滑块被顶起的高度」，
得到「格子盒 0.64 格 / 三角网格 0.0009 格」的惊人差距，
差点据此得出「应该换成三角网格」的结论。

问题是：起伏地形上滑块会**顺着坡真的往上爬**，那个高度和「被接缝顶起」混在一起了。
改到平坦地形重测之后，结论完全翻转 —— 格子盒 **0.00000 格**，三角网格 0.00074 格，
且格子盒构建快 2.3 倍、图元少 3 倍。

**规则**：基准要先问「我测的这个数，除了我想测的因素，还混进了什么」。
测不出差异比测出假差异安全得多。

### 教训三：以为「有测试」等于「测对了」

批量读位姿改造之后所有测试都过 —— 因为**没有一条测试比对过批量路径与逐个路径的结果**。
两条路径悄悄分叉的话，症状是「平时正常，只有批量读失败退回逐个读的那几帧位姿跳一下」，
这种偶发跳变几乎不可能被复现和定位。

**规则**：只要一个功能有「主路径 + 回退路径」，就必须有一条测试断言**两者等价**。

### 实证的四种形式

| 形式 | 用于 | 例子 |
|---|---|---|
| **单元测试** | 纯逻辑的行为契约 | `ViewLodPlannerTest` 的四道闸门 |
| **冒烟测试** | 子系统装配起来之后是否真的动 | `ObjectPhysicsWorldTest` |
| **对照测试** | 「开了这个开关到底有没有用」 | `InternalEdgeRemovalTest`（关 0.5183 格 / 开 0.0000 格）|
| **基准** | 选型决策的数据支撑，**不做断言** | `TerrainShapeBenchmarkTest` |

**基准与回归测试必须分清楚。** 基准的断言只守底线（「跑得起来」），
绝不断言「A 比 B 快」—— 那个结论会随机器、求解器参数、地形形状而变，
把它写成断言只会得到一条随机失败的测试。

## 5. 可测性下沉

这是项目最重要的一条架构纪律，也是模块划分的真正理由。

> **决策逻辑属于 `common`，发包与 Bukkit 调用属于 `paper`。**

`ViewLodPlanner` 是这条纪律的样板：「每个观众本帧该看到哪些东西、每个东西该做什么动作」
是纯计算，输入是平铺的 `double[]` / `boolean[]`，输出是动作掩码。
它零 Bukkit、零 packetevents 依赖，因此能用 JUnit 精确断言每一道闸门。
`paper` 层的 `ViewBroadcaster` 只负责把掩码翻译成发包调用。

**下沉的判据**：如果一段逻辑你想验证它，却发现「得先起一个服务器」，那它就下沉错了。

反过来也成立：**下沉不动的东西，就老实承认它测不了。** `paper` 模块没有测试源集，
物体物理线程的异常兜底（M6）就只能靠编译与代码审查验证 —— 这是事实，
写在文档里比假装有覆盖率强。

## 6. 质量门禁

一次改动要合入，必须全部通过：

- [ ] **全量测试绿。** `./gradlew build -PrunTests`
- [ ] **新增能力有对应的实证**（按 §4 的四种形式选一种或多种）
- [ ] **模块依赖方向没被破坏。** `api` 不依赖 `physics`；`common` 零 Bukkit 零物理实现；`paper` 零 `physics.engine` import；
      `physics` 零 Bukkit。破坏其中任何一条，下游插件就会被迫背上几十 MB 的三平台 native
- [ ] **native 资源有显式释放路径**，且释放顺序与构造顺序相反
- [ ] **跨线程字段标注了可见性**（`volatile` / 不可变发布 / 单线程独占），并在注释里写明谁读谁写
- [ ] **新增配置项写了注释**，说明默认值的由来与是否支持热重载
- [ ] **面向用户的行为变化已同步到 `docs/`**

### 关于 native 与线程的两条硬规则

这两类问题的共同点是：**错了不会编译失败，也很少立刻崩。**

**资源释放**：换成纯 Java 引擎之后，native 内存泄漏这一整类问题消失了。
但**显式 `close()` 仍是主线** —— 物理世界持有的数组与观众集合仍需及时释放，
靠 Cleaner 意味着释放时机完全交给 GC，堆外峰值不可控。
共享资源还要额外注意「谁拥有它」：`ClusterPhysicsWorld` 用 `ownsWorkspace` 标志区分
自建与共享，共享进来的绝不能在 `close()` 里关掉，否则会把其它还在跑的世界的
过滤表一起释放，native 侧直接段错误。

**线程纪律**：项目有三条线程 —— 主线程、坍塌物理线程、独立物体物理线程。
每个跨线程字段都要能回答「谁写、谁读、怎么保证可见」。
引擎对象**绝不跨线程裸传**，只传不可变快照。
Bukkit 的 `World`/`Block` 只能在主线程碰，所以地形流送是「主线程读方块算出 `float[]`
→ 队列 → 物理线程建刚体」这个形状，而不是更直观的那种写法。

## 7. 文档分工

四份文档，边界不重叠：

| 文档 | 回答什么 | 写给谁 |
|---|---|---|
| `DESIGN.md` | 当时是怎么想的、测出来是什么（**只追加**） | 未来的自己 |
| `docs/` 各系统文档 | 现在的系统是什么样、怎么配 | 服主与玩家 |
| Javadoc | 接口的精确签名与契约 | 下游插件开发者 |
| `docs/dev/` | 怎么做事（本文、贡献指南、发布流程、版本适配手册） | 贡献者与未来的自己 |

**判断一段内容该放哪**：它会随代码改动而失效吗？会 → `docs/` 或 Javadoc。
不会（它记录的是一个时间点的决策）→ `DESIGN.md`。

## 8. 一次完整迭代的样例

以 2026-08-06 那一轮（M1~M6）为例，对照上面每个阶段：

| 阶段 | 实际做了什么 |
|---|---|
| ① 调研 | GitHub 检索同类项目，确认 `rattle`（论点相同但已死三年）、`BlockPhysics`（Minestom，MIT）、`Velthoric`（需客户端 mod）三条路线的取舍 |
| ② 设计 | 通读全部 26k 行源码，产出分级问题清单（2 个 P0 / 4 个 P1 / 3 个 P2）与六项 MVP，明确不做「两世界合并」 |
| ③ 实现 | 按「低风险 → 内部优化 → 大改动面 → 依赖项」顺序逐项落地，每项跑全量测试 |
| ④ 实证 | 新增 5 个测试类：对照测试 1（内部边剔除）、等价性测试 1（批量/逐个读）、生命周期测试 1（共享 workspace）、闸门测试 4（资格掩码与槽位回收）、基准 1（地形形状） |
| ⑤ 归档 | 待补 `DESIGN.md` §25；配置注释已写；本文与[版本适配手册](version-migration.md)即为流程侧归档 |

**这一轮暴露的流程缺口**，已经在本文里补上了：

- 「实证」阶段原本没有「基准要先问混进了什么」这条 → 补进 §4 教训二
- 「主路径 + 回退路径必须测等价」原本是隐性共识 → 补进 §4 教训三
- 「配置项要写明是否热重载」原本没人管 → 补进 §6 门禁

## 9. 下一轮该做什么

按 §3 的分级，当前待办：

**P1 —— 有量化依据，等一个窗口**

- **带宽抓包校准**（`DESIGN.md` §14.5）。这是整套预算体系唯一还站在推算值上的地基，
  需要真机 + 抓包。在它完成之前，`budget.yml` 与 `view.yml` 的所有限额都是「待验证」。
- **L1 / L2 两档 LOD**。目前只有 L0，档位边界要等上一条的实测数据才好定。

**P2 —— 设计取向，需要单独立项**

- **两套物理世界合并**。坍塌碎块与独立物体目前物理上互不可见，
  这是玩法天花板。代价是重做局部坐标系（单精度构建的前提），需评估是否上 Dp 版。
- **贪心合并的地形网格**。当前基准结论是格子盒全面胜出，但基准没有做贪心合并 ——
  这是唯一可能翻转结论的变量。
- **增量式连通性维护**（`DESIGN.md` §17.5）。与 D2「事件驱动」的决策取向冲突，
  只有转向「全局常驻结构完整性」时才划算。

**持续 —— 见[版本适配手册](version-migration.md)**

- 26.3 正式版发布后的适配（分支已就绪，待真机验证）
- packetevents 的跟进节奏
