# 真实碰撞箱与交互系统

## 概述

物理化的方块默认是**看得见、走得过去**的：它们只是一批发给客户端的虚拟实体，服务端的方块表里那个坐标是空气。本系统把它们变成真的能撞到、能站上去、能被打飞的东西。

配置在 `collision.yml`，默认**全局启用**。

---

## 为什么碰撞箱不能搭骑乘组的便车

[骑乘组](../engine/view-packets.md)把「平移一整簇」的带宽从 O(方块数) 压到 O(1)，靠的是一个隐形根实体带着 N 个方块显示实体当乘客。但这个结构**给不了碰撞箱**，原因在客户端的定位逻辑：

```java
// 客户端每 tick 对每个乘客做的事
Entity.positionRider(passenger) →
    passenger.setPos(vehicle.getPassengerRidingPosition() - passenger.getVehicleAttachmentPoint());
```

`Transformation.translation`（乘客用来摆出簇内相对位置的那个分量）**完全不参与这条计算**——它只影响渲染。而 `BlockDisplay` 的实体类型是 `sized(0, 0)`，挂点是 `(0,0,0)`。

结论：**一个 64 方块的簇在客户端只有一个点有实体位置**，而且那个点的包围盒是零体积、`canBeCollidedWith` 恒为 false。

所以「方块真的挡住人」只有一条路：给每个方块一个**独立定位、独立收位置包**的实体。带宽因此从 O(簇数) 退回 O(方块数)——这就是本系统必须带预算的根本原因。

## 为什么是潜影贝

26.2 全原版里覆写 `canBeCollidedWith(Entity)` 并可能返回真值的只有三类（2026-08-26 在 `minecraft-merged-deobf-26.2.jar` 上逐条复核）：

| 候选 | 硬碰撞 | 尺寸 | 结论 |
|---|---|---|---|
| `Shulker` | ✅ `return isAlive()` | **1×1×1** | 采用 |
| `AbstractBoat` | ✅ 无条件 `return true` | 恒为 1.375×0.5625 | 铺不出方块格，且不是生物、无 `SCALE` 属性 |
| `HappyGhast` | ⚠ 成年 + 客户端侧 + **玩家在包围盒顶面之上** | 4×4（可用 `SCALE` 缩放，`sanitizeScale` 上限 1.0） | 单向平台语义：只能从上面站，侧面与下面都穿得过 |
| `AbstractMinecart` | ❌ 没覆写 | — | 只能推人，挡不住 |
| `Display` | ❌ 继承 `false` | 零体积 | — |

潜影贝的 1×1×1 恰好就是一格方块。`Entity.canBeCollidedWith` 的基类实现是 `return false`，所以没覆写就等于穿得过去。

### 只需要发两个包

生成包 + 一条隐形 metadata（`index 0` 的 byte 写 `0x20`）。其余全都不必：

- **血量**：网络默认就是 `1.0`（`LivingEntity.defineSynchedData` 里 `define(DATA_HEALTH_ID, 1.0F)`，已在 26.2 字节码上复核），`isAlive()` 已经为真 → `canBeCollidedWith` 返回 true
- **peek**：默认 0 时包围盒恰好是立方体，**且与吸附面无关**。一旦发了非 0，盒会沿吸附面的反方向长出最多一格
- **无重力 / 静音 / 无 AI**：客户端只对「本地权威」的实体跑 `travel()` 与 AI，而无乘客的远端实体永远不是

隐形**不影响碰撞**——`canBeCollidedWith` 只看 `isAlive()`。

### ⚠ 已知短板：没有客户端插值

26.2 的 `Shulker.getInterpolation()` 直接 `return null`，位置包一律**硬瞬移**。

（本项目早期注释里写过「Shulker 平滑度与 Display 相同」，那是错的，已更正。）

后果很具体：正在下落的碎块，碰撞箱每次广播阶跃一次，站在上面的玩家会被反复「顶起—掉落」。而已经停稳的废墟堆没有这个问题——它根本不再发位置包。

因此 `collision.yml` 给运动中的簇**单列了一档半径**（`moving-radius`）。

它的默认值与停稳档**取齐**（都是 8 格），而不是更小的 5：碎块下落速度轻易超过 10 m/s，5 格意味着它要等到贴脸才拿到碰撞箱、而下一帧就飞过去了——「物理化的方块能挡人」这件事在飞行阶段就基本不存在。

真机上若飞行中的手感糟糕（被反复顶起），把 `moving-radius` 调成 `0` 比调小干净得多：那样只有落定的废墟能站上去，飞行中的碎块仍然可以打、但不挡路。**调小只是把问题挪近**，阶跃本身还在。

### ⚠ 客户端会把潜影贝吸附到方块网格

`Shulker.setPos` 有一句覆写：

```java
super.setPos(Mth.floor(x) + 0.5, Mth.floor(y + 0.5), Mth.floor(z) + 0.5);
```

无论服务端发什么坐标，客户端都会把它对齐到最近的方块格。

这听起来像致命伤，对本项目**恰好是好事**：我们发的位置是「方块中心 − 半格」，代进那条公式原样返回——**格点对齐的碎块完全精确**，而玩家真正会踩上去的废墟堆本来就是格点对齐的。飞行中的碎块得到「最近那一格」的近似（最大误差半格），但它同时也**消除了抖动**——格点是稳定的，盒不会随亚格级位姿来回跳。对一个本来就没有插值的实体，这反而更好。

**服务端按同一条公式先吸附一次**，所以攻击判定用的盒与玩家看到的那个是同一个。少了这一步会出现最难解释的一类现象：明明瞄准了、点中了，射线却从旁边擦过去。

唯一要记住的是：**盒永远轴对齐且格点对齐**，一块斜着飞的方块，碰撞盒不会跟着倾斜。

## 两级剔除与预算

一场坍塌可以有上千个方块，而逐槽计算世界坐标需要一次四元数旋转。规划器（`common/collision/ColliderPlanner`，可脱离服务器单测）因此做两级剔除：

1. **簇级**：簇质心到玩家的距离若已超过 `半径 + 簇半径`，簇里任何一个方块都不可能进入半径——整簇一次判掉，一次旋转都不用做。
2. **槽级**：跨过第一道闸门的簇才逐块算世界坐标，再过距离闸门。

然后用**容量等于预算的最大堆**挑出最近的 K 个：一趟 O(n log K) 扫完，稳态零分配。

### 资格掩码取自视觉可见集

碰撞箱与视觉是两套独立的逐观众状态。一旦不同步就会出现本项目最难排查的一类投诉：**看不见但撞得到**（碎块被墙遮住而没生成，碰撞箱却还在那里挡人）。

所以每帧把视觉规划器**本帧结束后**的可见集导出成碰撞箱的资格掩码——两者因此恒等地取了交集。玩家看得到的东西才可能挡住他。

## 攻击与右键

### ⚠ 26.2 的协议断层

从 26.1 起，**攻击不再走 `INTERACT_ENTITY`**，而是独立的 `ATTACK` 包（包体只有一个实体 ID）。而 packetevents 的 `WrapperPlayClientInteractEntity` 在新版本分支里把 action 硬写成 `INTERACT_AT` 作为兼容值。

照老教程写「监听 `INTERACT_ENTITY` 再判 `action == ATTACK`」在 26.2 上**永远不会为真**——编译通过、不报错、就是打不动。所以本系统同时监听两个包类型。

### 三跳链路

```
netty 线程 : 一次整数比较认出虚拟实体 → 查并发表 → 打包成基本类型
主线程     : 查表、求命中点、触发可取消的 PhysicsBlockHitEvent、算冲量
物理线程   : 在步进边界把冲量施加到刚体
```

每一跳都是必须的。在 netty 线程碰 Bukkit 是未定义行为；在主线程直接写刚体会与 40 Hz 的物理步进抢同一批 double 字段——撕裂的位姿最轻是碎块抖一下，最重是求解器拿到 NaN 之后整簇消失。

代价是天然带一 tick 延迟。对「一拳把方块打飞」这件事，那是察觉不到的。

### 第一道闸门是一次整数比较

虚拟实体 ID 从 `2^27` 递减分配，原版从 1 递增，两端相隔 6700 万。于是 `entityId > (1 << 26)` 这一条 `if` 就能把玩家打怪、打人的绝大多数交互包挡在门外——**根本不会走到反查表**。

### 命中点决定力臂

攻击包不带命中点，服务端用玩家视线对**那一个盒**求交（既然 ID 已经唯一确定了是哪个盒，就不必做全场射线检测）。

命中点决定力臂：打在边角上方块会转起来，打正中间就平平飞出去。求交失败时（客户端与服务端对盒位置的认知差了一个广播间隔）退化成盒心——那一击打不出旋转，但总比「打了没反应」好。

### 冲量按单块质量折算

配置项 `attack-speed` 的语义是「一拳能把**一格**方块打到多少 m/s」。

```
J = attack-speed × 每方块质量
```

于是打一整面 64 格的墙时，它只能获得 `4/64 ≈ 0.06 m/s`。这正是应该的——墙比一块砖重 64 倍。不需要任何特判，是 `Δv = J/m` 自己给出来的。

用速度而不是直接配冲量（N·s），是因为速度是服主唯一能凭直觉判断的量。配冲量的话，得先知道「一格石头有多重」（2500 kg）才填得出合理值。

## 常驻物体：按外形分两档

骰子、载具、布娃娃、物理 TNT 走的是另一条链路，但用的是同一个 `ColliderSwarm`。它们**逐槽**按外形决定拿哪一种盒：

| 外形 | 实体 | 能挡人 | 盒 |
|---|---|---|---|
| 接近一格立方（物理 TNT、方块型小物件） | 隐形潜影贝 | ✅ | 恒 1×1×1，吸附到方块网格 |
| 异形（载具、布娃娃） | `Interaction` | ❌ 只能被打中 | 逐个设宽高，贴合外形 |

判据在 `ColliderSettings.isBlockShaped(width, height)`：宽高都在 1 格 ±0.15 内即算方块形。容差取 0.15 是因为半格以内的误差与「客户端吸附到网格」本身带来的误差同一量级，再严格没有意义。

分两档的理由是形状：碎块是一格一格的，1×1×1 严丝合缝；而一辆 3×1.5 的车套上同一个实心盒，得到的是「明明走得过去却被卡住」与「明明该挡住却穿过去」的混合体——**比没有碰撞更糟**。`Interaction` 的盒能贴合外形，代价是不挡人；对「能不能打中那辆车」这个需求，贴合比阻挡重要得多。

> 从前这里是**整群**硬降级：`ViewBroadcaster.objectMode()` 一句 `return INTERACTION` 把所有常驻物体的碰撞一并关掉，连一枚正正一格的物理 TNT 都拦不住玩家。

**命中判定必须跟着走同一份判据**。潜影贝那一档的盒被客户端吸附到格点且恒为 1×1×1，服务端求交时若还按物体自报的 3×1.5 算，就会出现「玩家明明点中了却毫无反应」。所以 `colliderBox()` 读的是**发包用的同一个数组**，而不是就地重算。

两种盒都是**轴对齐**的，物体翻滚时并不跟着转。对近似立方的东西影响很小；对细长的载具，最坏情况下判定盒会比车身宽出一截。这是协议天花板，不是实现偷懒。

## 给插件开发者

每次命中都会触发可取消的 `PhysicsBlockHitEvent`（在 `api` 模块，主线程同步）。

物理化的方块不在世界上，所以原版的 `PlayerInteractEvent` / `BlockBreakEvent` 永远不会为它触发——**领地保护插件唯一的拦截点就是这个事件**。

事件还允许改写这一击的速度增量：设成 0 就是「判定成立但打不动」，适合做「需要特定工具才能击碎」这类玩法。

详见 [API 指南](../api/index.md)。

## 带宽

| 包 | 字节 |
|---|---|
| 生成 + 隐形 metadata | ≈ 65 |
| 绝对位置包（`EntityTeleport`） | 66 |

96 个盒在 10 Hz 下的**峰值**约 63 KB/s/人。这只在「一大团碎块正贴着你飞」的那几秒出现；稳态接近 0，因为玩家真正会踩上去的废墟全是停稳的簇，规划器对它们只补一帧终态就停发。

### 虚拟实体 ID 的消耗

碰撞箱每个方块一个 ID，且 ID 从 `2^27` 递减、**永不回收**。开启碰撞后一场坍塌的 ID 消耗大致翻倍。按 1.34 亿的池子算仍有很大余量，但长期不重启的服务器值得留意（`/gtrp status` 里可以观察）。

## 已知边界

| 项 | 说明 |
|---|---|
| 碰撞箱没有客户端插值 | 见上文。运动档默认与停稳档取齐（8 格）；嫌抖把 `moving-radius` 调 0，不要调小 |
| 服务端不知道碰撞箱存在 | 玩家站在半空中的碎块上时，服务端的飞行检测可能在约 80 tick 后把他拉回。坍塌那几秒不会触发，长时间站在废墟顶上可能会 |
| 隐形潜影贝会「软推」玩家 | 原版的实体互推只有水平分量，所以「碎块把人横向挤开」是免费的，「人站在移动的碎块上被带着走」不是 |
| 攻击判定有半拍误差 | 服务端算的是最新盒位置，客户端看到的是上一次广播的位置。快速下落的碎块上两者会差 0.5~1 格——碰撞箱只在近距离激活，正是为了压住这个误差 |
| 投掷物打不中 | `Interaction.canBeHitByProjectile()` 在 26.2 返回 false；潜影贝则会被箭矢命中但那是「攻击一个生物」的语义，本系统不接管 |
