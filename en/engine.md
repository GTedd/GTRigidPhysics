# 引擎总览

GTRigidPhysics 的物理引擎是**自研的、纯 Java 的**，不依赖任何原生库。
整个引擎是 `physics` 模块下的 24 个类，编译产物随插件 jar 一起分发，没有 `.dll` / `.so` / `.dylib`，也不需要 `--enable-native-access`。

!!! info "它曾经不是这样"
    早期版本用的是 jolt-jni（Jolt Physics 的 Java 绑定）。2026-08-20 整体迁移到自研 XPBD 求解器。
    迁移的动机、取舍与实证记录在仓库内的 `docs/internal/物理引擎重构调研报告.md`（不进公开站）。
    如果你在别处读到「GTRigidPhysics 基于 Jolt」，那是过时的说法。

## 为什么要自己写

通用物理引擎解决的是通用问题。而这个插件面对的世界有三条极强的先验：

1. **一切碰撞体都是轴对齐盒的并集。** 体素世界里没有真正的凸包 —— 整块是一个盒，台阶是两个，楼梯是三个。
2. **地形建好就不再变。** 一场坍塌里静态盒可以上万，但它们在这几秒内一个都不会动。
3. **坍塌同时踩中大质量比与深堆叠。** 一块石头压着一片玻璃，废墟能堆七八层。

通用引擎必须放弃前两条先验（它不知道你的世界是体素的），而第三条恰恰是顺序冲量法最吃力的场景。
自己写的收益不是「更快」这么笼统，而是三条具体的东西：

| 收益 | 来自哪条先验 |
|---|---|
| 内部面在建形状时就被剔除，**幽灵碰撞被根治**而不是被参数掩盖 | 1 + 2 |
| 地形查询退化成「按格子取一小撮候选盒」，是 O(1) | 2 |
| 深堆叠靠「多子步 + 少迭代」稳住，而不是靠堆迭代次数 | 3 |

外加两个非物理的收益：**零原生依赖**（不再有 `hs_err` 崩溃、不再有平台分发矩阵），以及**测试可以在普通 JVM 里跑**——`physics` 模块的 9 个测试类不需要任何原生库。

## 一次模拟步

物理运行在独立线程上，频率 **40 Hz**（`PhysicsDriver.SIMULATION_HZ`），即每个服务器 tick 走 2 步。
每一步再切成 8 个子步（`XpbdSolver.SUB_STEPS`），所以积分的实际频率是 **320 Hz**。

```
一个外层步（1/40 秒）
├─ 重置本步撞击记录
├─ for 子步 in 1..8:               ← 每个子步 1/320 秒
│    ① 积分      重力 + 二次空气阻力，半隐式欧拉推进位置与姿态
│    ② 生成接触  刚体 vs 地形、刚体 vs 刚体 → 一组接触约束
│    ③ 位置求解  ×4 迭代，把接触与约束投影掉
│    ④ 速度反推  v = (x − x_prev)/h，角速度由姿态差的四元数虚部得出
│    ⑤ 速度求解  ×8 迭代，恢复系数（弹性）与库仑摩擦
└─ 休眠判定
```

第 ④ 步是 XPBD 与冲量法最根本的分歧：**速度不是被积分出来的，而是被位置变化反推出来的**。
详见 [XPBD 求解器](xpbd.md)。

## 两种运动模型

引擎只提供两种基础运动模型，其余都是它们的组合：

| 运动模型 | 平动 | 转动 | 实现 |
|---|---|---|---|
| **质点** | 支持 | 不支持 | `RigidBody` 的惯性张量逆置零 —— 力矩不再改变姿态 |
| **刚体** | 支持 | 支持 | 完整 6 自由度，`MassProperties` 给出的 3×3 惯性张量 |

刚体的 `kind` 字段还区分三种参与方式：

| `kind` | 含义 |
|---|---|
| `DYNAMIC` | 受力、受碰撞、会休眠。碎块、骰子、载具车身 |
| `KINEMATIC` | 位姿由外部直接写入，能推动 `DYNAMIC` 但不被推动。活塞的驱动端、被玩家抓住的物体 |
| `STATIC` | 永不移动。地形之外的固定锚点 |

## 那些写死的数字

引擎里有一批常量刻意**不做成配置项** —— 它们是求解器的稳定性参数，改了不是「换一种手感」而是「解不出来」。
列在这里是为了让改引擎的人知道它们存在，以及动它们要付出什么。

| 常量 | 值 | 动它会怎样 |
|---|---|---|
| `XpbdSolver.SUB_STEPS` | 8 | 调小，深堆叠开始抖；调大，CPU 线性上涨 |
| `XpbdSolver.POSITION_ITERATIONS` | 4 | 调小，平拍落地的方块会残留姿态误差并被 1/h 放大成假旋转 |
| `XpbdSolver.VELOCITY_ITERATIONS` | 8 | 调小，史莱姆方块落地几乎不弹（雅可比单次是欠松弛的） |
| `XpbdSolver.MAX_DEPENETRATION_PER_SUBSTEP` | 0.05 格 | 调大，密堆物体会攒出巨大位置修正并炸开 |
| `XpbdSolver.MAX_DEPENETRATION_SPEED` | 1.5 m/s | 同上。注意它**只夹去穿透那一部分，不动真实动量** |
| `XpbdSolver.MAX_DEPENETRATION_SPIN` | 2.0 rad/s | 同上，作用在旋转上 |
| `XpbdSolver.ANGULAR_NOISE_EPS` | 0.0025 rad/s | 关掉，静止碎块会极慢自转、永不休眠 |
| `XpbdSolver.RESTITUTION_THRESHOLD` | 0.5 m/s | 关掉，静置物体永远轻微弹跳、永不休眠 |
| `XpbdSolver.STATIC_FRICTION_SLIP_LIMIT` | 1.0 m/s | 关掉，高速滑行的方块会转而翻滚，滚得比滑得还远 |
| `ContactGenerator.SPECULATIVE_DISTANCE` | 0.05 格 | 调小，高速物体开始穿透 |
| `ClusterPhysicsWorld.MAX_BLOCK_SPEED` | 39.2 m/s | 原版落体终速。调大，碎块会比原版落沙先着地 |
| `ClusterPhysicsWorld.BASE_MASS_PER_BLOCK` | 1000 | 质量基准。`materials.yml` 的 `density` 乘在它上面 |
| `PhysicsDriver.SIMULATION_HZ` | 40 | 物理线程频率。见下方说明 |

!!! warning "40 Hz 不等于网络频率"
    物理算 40 Hz，但位姿**广播**默认是 10 Hz（`view.yml` 的 `broadcast-interval-ticks: 2`）。
    两者刻意不相等：网络是本项目的首要约束，多算出来的精度用于让碰撞正确，而不是全部发出去。
    调高 `SIMULATION_HZ` 不会让画面更平滑，只会更费 CPU。

真正开放给服主的旋钮在 [配置指南](../guide/config/index.md)，物理相关的集中在 `physics.yml` 与 `materials.yml`。
