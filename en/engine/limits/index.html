    性能与上限🔗

    数据来源：PhysicsDriver 的实测注释、physics 模块的标定测试、 以及 2026-08-20 自研引擎整改的实证记录

    这一页回答三个问题：它能扛多少、瓶颈在哪、哪些偏差是已知且不打算修的。

    这一页的数字有的是实测，有的是推算

    实测的会写明来源。没有标注来源的是从实测值线性外推的估计，不要当作承诺。

    硬上限🔗

    这些是代码里写死的边界，超过就是另一种行为，不是「变慢一点」。

    上限 值 出处 超出会怎样
    独立物体世界的刚体总数 max-bodies: 4096 physics.yml 建不出新刚体 —— 表现为物体脚下突然没有地面、直接穿下去
    独立物体数 256 MAX_ACTIVE_OBJECTS 按生成顺序淘汰最老的
    布娃娃 32 具 × 7 部件 = 224 预留额度 拒绝生成
    虚拟角色 64 预留额度 拒绝生成
    单个形状的采样点 2048 BodyShape.MAX_SAMPLE_POINTS 退化为只取角点（安全，见碰撞形状）
    地形稠密格 2²¹ TerrainField.MAX_CELLS 全部降级为大盒逐个测
    单簇方块数 64（网格切分）/ 256（整根构件） analysis.yml / structure.yml 超出退回网格切分
    单次分析的簇数 512 analysis.yml 的 max-clusters WARN + 留下部分悬空方块
    刚体速度 39.2 m/s MAX_BLOCK_SPEED 夹住。这是原版落体终速
    单场坍塌时长 15 秒 physics.yml 强行定格并就地写回，表现为悬空方块
    物理世界数 8 MAX_WORLDS 复用最后一层 + 警告，这几个世界之间会互撞
    节拍积压 8 帧 MAX_PENDING_STEPS 丢帧，模拟整体放慢

    实测性能🔗

    场景 数字 来源
    1000 刚体单步耗时 1.07 ms PhysicsDriver 注释
    40 Hz 下物理线程占用 约 4.3% 单核 同上
    插件 jar 体积 754 KB（整改时）/ 843 KB（当前构建） 构建产物
    native 二进制 0 jar 内容
    测试总数 326（common 212 + api 65 + physics 49） 整改验收

    零 native 的连带收益

    • 平台限制消失：macOS、Windows-ARM 现在都能跑
    • 求解器测试在普通 JVM 里跑，不需要服务器、不需要原生库
    • 不再有 hs_err 崩溃 —— 纯 Java 没有悬垂指针

    瓶颈在哪🔗

    按实际吃掉预算的顺序排：

    1. 网络，不是 CPU🔗

    这是本项目的首要约束，写在 DESIGN.md 的第二节。

    物理算 40 Hz，广播只有 10 Hz，而且还有五道闸门在压： 距离剔除、观众上限、旋转配额、区域预算池、遮挡剔除。

    旋转是带宽的大头

    平移整个簇只要 1 个包；旋转要给每个方块各发一次 metadata。

    256 个方块的姿态关键帧约 18 KB，按 2 Hz 发就是 36 KB/s —— 已经吃掉单个玩家物理带宽预算（50 KB/s）的一大半。

    这就是 budget.yml 的 max-rotating-blocks-per-player 单位是方块而不是簇的原因。

    调参入口见性能与预算。

    2. 主线程的方块读写🔗

    不是物理线程。三处都在主线程且都必须限流：

    操作 限流项 默认
    落地写回 settle.yml 的 blocks-per-tick 150
    撞击破坏 impact.yml 的 blocks-per-tick 4
    地形流送建格 MAX_BUILDS_PER_REFRESH 6

    setBlockData 会触发光照更新与区块标脏 —— 不限流一次大坍塌就能卡住主线程。

    3. 求解器本身🔗

    只有在碎块数上千时才成为瓶颈。两处已知的未优化：

    • 广相是 SAP 而非空间哈希。按 X 轴排序 + 扫描，对「碎块沿地面铺开」的分布够用，碎块数上千时应当补上。
    • 岛并行未实现。PhysicsWorkspace.workerCount（即 physics.yml 的 workers）目前只是个建议值，求解仍是单线程。留了落点，未接线。

    已知偏差🔗

    这些是已经量化过、并且接受的偏差。真机调参之前先读一遍，否则会把它们当成 bug 去追。

    恢复系数收敛不足🔗

    值
    配置 bounciness: 0.8
    实测有效 约 0.63

    源于雅可比平均是欠松弛的。史莱姆方块明显会弹（回弹 2.5 格），但比标称值偏低。

    把 VELOCITY_ITERATIONS 从 8 提到 16 能逼近 0.75，代价是 CPU。

    动摩擦偏低🔗

    值
    配置 μ = 0.75
    实测有效 约 0.52（在 [0.6, 1.6] 倍的验收窗口内）

    同样源于雅可比欠松弛。相对关系是正确的：冰 32.8 格 / 石 3.6 格 / 蜜 2.6 格。

    调参时按相对关系调，不要按绝对值调。

    碎块落坑容差🔗

    对角 0.04 格、单轴 0.04 格。

    单轴那一档确实退步了（原生引擎时代是 0.24）。坑宽 1.0、碎块 0.92， 几何上任何超过 8.7° 的倾斜都会卡在坑口，只能「基本不转地平移进去」。

    只影响飞行途中的观感

    落地写回由 SettlePlanner.sinkToSupport 兜底，不会留下错位的方块。

    圆柱是近似🔗

    用「侧面圆角的方柱」近似，不是真圆柱面。

    硬币、滚木在体素尺度上看不出差别；真要精确圆柱得单开一类碰撞原语。

    凸包是半精确🔗

    作为运动的一方精确（顶点即采样点），作为被压的一方退化成包围盒。

    凸包用于被扔来扔去的小物件，很少充当承重面。

    载具是街机模型🔗

    VehicleSettings 的变速箱、差速器、防倾杆、摩擦曲线全部被忽略。 详见载具 · 有一半字段不再生效。

    与通用引擎的差距在哪🔗

    诚实地讲：单体性能不如 Jolt。纯 Java 无 SIMD，每个刚体的成本更高。

    补偿手段是四样，全部已落地：

    1. 贪心合盒 —— 25 个单位盒合成 1 个，采样点 650 → 26（详见）
    2. 地形独立索引 —— 上万个静态盒不进广相两两测试
    3. 休眠 —— 一场坍塌的正常结束条件就是全部休眠
    4. 预算闸门 —— 五道，见性能与预算

    而在两处赢过通用引擎：

    为什么赢
    幽灵碰撞 体素世界的内部面是已知事实，不用启发式去猜（详见）
    深堆叠 + 大质量比 XPBD 的「多子步 + 少迭代」正好对上坍塌的形态（详见）

    怎么观察运行时占用🔗

    /gtrp status

    它会给出物理线程耗时、活跃刚体数、四个预算指标的占用率。 调参前后各跑一次对比，比凭感觉可靠。

    详见性能与预算。
