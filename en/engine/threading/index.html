    线程与数据流🔗

    源码：physics/PhysicsDriver.java、physics/PoseSnapshot.java、paper/scheduler/Schedulers.java

    三条线程、四种数据形态、五条跨线程通道。这一页是改引擎之前必须读的一页 —— 这里的每一条纪律都对应一个曾经真实发生过的缺陷。

    三条线程🔗

    线程 频率 干什么
    主线程（MC tick） 20 TPS 读写方块、发包、发节拍、消费快照
    物理线程 40 Hz 步进全部物理世界，产出位姿快照
    异步分析线程 按需 结构完整性分析（纯计算，零 Bukkit）

    为什么物理频率必须是 20 的整数倍🔗

    这不是性能考量，是平滑度的硬前提

    MC 是 20 TPS，位姿广播每 N 个 tick 一次。 只有当物理频率是 20 的整数倍时，每次广播才恒定地跨越相同数量的物理帧。

    反面教材：本项目最初的 25 Hz🔗

    广播每 2 tick（0.1 秒）一次，而 0.1 秒里物理走 2.5 帧。 于是每次广播跨越的帧数在 2 和 3 之间来回跳，位移量忽大忽小 50%。

    客户端插值只能把每一段各自抹平，抹不掉段与段之间的速度突变 —— 肉眼看到的就是碎块一顿一顿地往下掉。

    为什么是 40 而不是 20🔗

    碎块自由落体末速可达 20 m/s：

    • 20 Hz 下单帧位移一整格，薄地形会被穿透
    • 40 Hz 下单帧半格，安全得多

    实测 1000 刚体单步 1.07 ms，40 Hz 下物理线程占用约 4.3% 单核。

    节拍由主线程给，不用 wall clock🔗

    物理线程不自己计时，而是等主线程每个 MC tick 发来的节拍信号。

    为什么不能 Thread.sleep🔗

    Thread.sleep 在 Windows 上的时钟粒度约 15.6 ms，而 40 Hz 的周期只有 25 ms —— 睡 25 ms 实际可能睡 31 ms。

    追帧逻辑能保证平均帧率正确，但瞬时帧率一直在抖。 于是主线程每次广播时取到的「最新帧」跨越的物理帧数在 3~5 之间浮动，位移量随之忽大忽小。 这正是碎块下落看起来一顿一顿的根因之一。

    MC 的 tick 是稳定的 50 ms 节奏，拿它当时钟源比任何 sleep 都准。

    附带好处

    服务器卡顿时物理自动跟着慢下来，视觉上是整体放慢而不是突然跳帧。

    积压上限🔗

    若主线程连续多次 tick 而物理没跟上，节拍会积压。 超过 MAX_PENDING_STEPS = 8 的部分直接丢弃 —— 宁可让模拟慢下来，也不能让物理线程陷入「一次要补几十步，越补越慢」的雪崩。

    为什么是一条线程驱动全部🔗

    多场坍塌各开一条线程会让线程数随事件数增长，而它们彼此完全独立、单场的求解代价又很小 —— 外层堆线程只会互相抢核心。

    所以外层保持单线程串行驱动；需要并行时在求解器内部按接触岛切分。

    physics.yml 的 workers: 2 说的是后者，不是「开两条物理线程」。

    四种数据形态🔗

    形态 实现 生命周期 线程约束
    配置 PluginConfig（不可变） 插件生命周期 只读，线程安全
    运行实例 PhysicsObject / CollapseSimulation 物体 / 坍塌生命周期 主线程独占
    求解器状态 RigidBody / ContactSet 物理帧内 物理线程独占
    跨线程快照 PoseSnapshot（不可变 record） volatile 引用，单帧 任意线程只读
    世界快照 int[] palette 数组 一次分析 异步线程只读

    配置🔗

    config.yml 只存统筹项（语言、禁用世界）。各功能域独立成文件，共 14 个， 由 /gtrp admin reload 热重载。完整清单见配置总览。

    所有解析都带默认值兜底：文件被删掉某一项或整个文件缺失时退回默认值， 而不是抛异常导致插件加载失败。

    PoseSnapshot🔗

    public record PoseSnapshot(
        double[] positions,    // 3N，第 i 个刚体是 [i*3 .. i*3+2]
        float[]  rotations,    // 4N，四元数 x,y,z,w
        boolean[] active,
        float[]  peakSpeeds,
        float[]  speeds,
        int      count,
        long     frame) {}

    物理线程每步进完一帧，把结果拷成一个新对象，然后原子发布（volatile 引用赋值）。 主线程只读最新发布的那一份。

    没有锁、没有竞态 —— 主线程最坏情况只是读到上一帧，而这对 5~10 Hz 的发包节奏完全无所谓 （客户端本来就在插值补帧）。

    为什么两种速度都要带着

    它们服务于两个不同的时刻，缺一不可：

    • peakSpeeds（沿途最大速度）给落地判定用。落地发生在主线程、且在刚体休眠之后， 那一刻的瞬时速度恒为 0；只看瞬时速度的话，从三十格摔下来的树叶和原地放置的树叶没有任何区别。
    • speeds（本帧瞬时）给过程中的表现用（下落拖尾、撞击反馈）。这里反过来不能用峰值： 一个曾经飞快、此刻正在地上慢慢滚的碎块峰值仍然很高，照着它扬灰就会「停下来了还在冒烟」。

    五条跨线程通道🔗

       主线程 (20 TPS)          物理线程 (40 Hz)         异步分析线程
        │                        │                        │
        │  ① 节拍信号            │                        │
        ├───────────────────────►│                        │
        │                        │                        │
        │  ③ PoseSnapshot        │                        │
        │◄───────────────────────┤  (volatile publish)    │
        │                        │                        │
        │  ② 提交分析任务        │                        │
        ├────────────────────────┼───────────────────────►│
        │                        │                        │
        │  ④ AnalysisResult      │                        │
        │◄───────────────────────┼────────────────────────┤
        │                        │                        │
        │  ⑤ 命令队列（建/删刚体、施力）                   │
        ├───────────────────────►│                        │
    通道 方向 载荷
    ① 主 → 物理 tick 节拍。物理线程收到后推进 STEPS_PER_TICK = 2 帧 × timeScale
    ② 主 → 异步 区域 AABB + 扁平 int[] palette 快照
    ③ 物理 → 主 PoseSnapshot，volatile 发布
    ④ 异步 → 主 AnalysisResult（失联簇列表），回调到主线程
    ⑤ 主 → 物理 命令队列，排到步进边界执行

    线程纪律🔗

    引擎对象绝不跨线程裸传🔗

    物理线程只产出不可变的 PoseSnapshot（原始数组）。

    ObjectPhysicsWorld 的整套 API 只收发 double、float 与 id —— RigidBody、ContactSet、求解器常量一个都不出现在签名里。

    这是一道结构性的墙，不只是约定

    从前这套东西整个长在 paper 里（两千多行，通配符 import 了整个原生引擎的包）， 平台层与物理层彻底纠缠。收到这道墙后面是引擎重构的主要结构性收益之一。

    构建里有 forbidden-import 检查守着这条线。

    异步分析线程绝不碰 Bukkit 对象🔗

    分析线程只读扁平化的 int[] palette 快照 —— 区域方块数据在快照时已经从 Bukkit 对象里解析出来了。

    任何 Bukkit API 调用都在主线程完成。

    违反的后果不是「偶尔读到脏数据」这么轻：异步触发区块加载会直接崩服。

    增删刚体只能在步进边界🔗

    主线程要改什么，走命令队列排到两帧之间执行。

    地形操作排在物体入队之前：新生成的物体应该在第一帧就能撞到地面， 反过来的话它会先自由落体一帧。

    onDisable 顺序不可调换🔗

    1. 销毁全部虚拟实体   ← 需要 packetevents 存活
2. 停止物理线程       ← 不再产生新的 PoseSnapshot
3. 关闭物理世界

    packetevents 不在这里关 —— 它是独立前置插件，因 load: BEFORE， 其 onDisable 会在本插件之后自行执行，恰好满足「发包层最后关」。

    自研引擎让这条纪律不再致命

    从前顺序错了会在 native 侧留下悬垂指针（对已 close 的 PhysicsSystem 调 setGravity 会写 0x520， 直接崩 JVM）。现在最坏是发包失败打一条日志 —— 纯 Java 没有悬垂指针。

    纪律仍然要遵守，但代价从「崩服」降到了「一条 warning」。

    两套物理世界的隔离🔗

    世界 类 用途 生命周期 地形
    坍塌世界 ClusterPhysicsWorld 建筑倒塌碎块 按事件创建 / 销毁 TerrainField，开场一次性建好
    物体世界 ObjectPhysicsWorld 骰子 / 载具 / 机关 / 布娃娃 / 角色 进程级 静态刚体，流式增删

    两套世界由同一个 PhysicsDriver 驱动（共享物理线程、分别步进），但完全独立 —— 坍塌的碎块不会撞到玩家投掷的骰子。

    坍塌世界用局部坐标（原点在分析盒中心），物体世界直接用世界坐标。 前者是为了让坍塌在任何世界坐标下都有相同的数值条件。
