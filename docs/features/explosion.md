# 爆炸飞溅系统

## 概述

原版的 TNT 炸墙，观感是「墙上出现一个洞」——方块直接从世界上消失，按 `yield` 概率掉几个物品。

本系统**不动那个洞**。被爆炸射线打穿的方块照原版处理：照常消失、照常掉落。真正接管的是**弹坑外面那一圈**——射线打到了、但没打穿的那一层。它们被冲击波掀起来，变成受径向冲量的物理刚体飞溅出去。

实现类：`paper/collapse/ExplosionDebrisService`（把方块送上天），选哪些方块由 `CollapseTriggerListener` 决定。

!!! note "为什么不接管弹坑本身"
    早期版本把 `blockList()` 整份接管过来变成飞溅碎块。问题是那批方块正是被射线打穿的部分，它们在观感上**本来就该没了**——物理化只是把「一个洞」换成「一堆从洞里飞出来的方块」，既丢掉了原版掉落，又要为每一块付两个虚拟实体。

    而且贴地爆炸时，弹坑里绝大多数方块是**地基**：四面被土石夹着，冲量根本推不动，模拟几百帧之后原地落回原位，玩家只看到它闪了一下。纯粹是白烧刚体。

---

## 爆炸有三条独立的链路

同一次爆炸会走三条完全不同的路径，它们回答的是不同的问题：

| 链路 | 回答的问题 | 处理对象 | 实现 |
|---|---|---|---|
| **原版破坏** | 哪些方块被**炸穿**了 | `EntityExplodeEvent.blockList()` | 原版，我们不碰 |
| **冲击波飞溅** | 弹坑外哪一圈被**掀起**了 | 弹坑的六邻域 | `collectShell` → `ExplosionDebrisService` |
| **坍塌** | 爆炸之后哪些方块**失去了支撑** | 结构分析的结果 | `CollapseService` → `StructuralAnalyzer` |

炸墙时：洞是原版的产物，洞边缘四散飞出的墙皮是②的产物，洞上方那截失去支撑而垮下来的墙是③的产物。

②③ 共用同一个 `RigidCollapseExecutor`，因此碎块的表现层、落地规则、破碎判定完全一致。

## 壳层怎么选

### 以弹坑为种子，而不是画一个球

原版的破坏名单**本身就是爆炸射线的覆盖结果**——它随方块爆炸抗性而凹凸不平，石头挡得住的地方坑就浅。沿这份名单向外扩一层（只走六个面，斜角相邻挡不住冲击波），拿到的正是「射线打到了但没打穿」的那一层，形状天然跟着射线走。

```java
private static final int SHELL_LAYERS = 1;      // 「外一圈」= 1
private static final int MAX_SHELL_BLOCKS = 96;
```

从前这里画的是一个半径 `威力+1` 的实心球，把范围内所有实心方块全部拉进物理世界——包括爆心下方推不动的地基。

### 贴地爆炸只取上半球

TNT 放在地面上时，弹坑是往下挖的，它的壳层有一大半埋在土里。那半圈四面受夹，冲量推不动，是「物理化再实体化」里最没意义的一批。

因此：探到脚下有地面时（向下最多看 `GROUND_PROBE_DEPTH = 2` 格），**丢弃地面高度以下的壳层方块**，只留地表那一圈及以上——也就是上半球。

悬空爆炸（脚下探不到地面）不做这个裁剪，壳层保持完整球形。

!!! warning "地面高度必须在事件里探"
    等原版把坑炸出来就探不到原来的地面了，所以 `groundSurfaceY()` 在 `EntityExplodeEvent` 里就要跑完，把结果带进下一 tick。

### 推不动的不物理化

即使在上半球里，也还有夹死在实心中的方块（墙体内部、洞穴顶）。`canBeEjected` 给两条出路，有一条就够：

- **头顶是空的** —— 能被掀起来。地表弹坑那一圈几乎都走这条；
- **径向外侧是空的** —— 头顶压着东西时，只能顺着冲击波往外挤，外面得有空间。

两条都不满足的直接跳过：生成刚体、生成虚拟实体、算几百帧，最后被四周挤回原位再写回去，玩家只看到它闪了一下。

## 时序：为什么要等一 tick

```
EntityExplodeEvent (MONITOR)
  ├─ 视角滚转
  ├─ 记下 blockList() 的位置（不修改它！）
  ├─ groundSurfaceY()               ← 必须趁地面还在
  └─ 排两个下一 tick 的任务

下一 tick
  ├─ launchShockwave                ← 此刻弹坑已经是空气
  │    ├─ collectShell              ← 弹坑六邻域 + 上半球 + 推得动
  │    ├─ debris.launch             ← 物理化飞起
  │    └─ clearSuspended            ← 逐层向上，处理失去支撑的
  └─ 结构分析：整体失联的簇 → 坍塌物理化
```

`EntityExplodeEvent` 触发时原版**还没删方块**。此刻拍快照的话，弹坑仍是实心的——壳层方块一物理化就被困在自己旁边那堵「马上要消失的墙」里，飞不出去。等一 tick，坑真的空了，壳层才有地方可去。

两个任务都走 `Schedulers.run`，FIFO 入队，所以飞溅先跑、结构分析后跑：分析看到的世界里，壳层已经被摘走了。

---

## 没接管的方块怎么办

`launch()` 会就地修改传入的集合：接管的移除，剩下的交回调用方。**两条调用路径的处置方式刻意不同**：

| 路径 | 没接管时 | 理由 |
|---|---|---|
| 壳层飞溅 | **原样留着**，不删也不飞 | 它们不在原版破坏名单里，删掉等于凭空扩大爆炸范围 |
| 悬空清理 | **直接删成空气** | 它们已经没有支撑，留下来就是浮空 bug |

数量上限：

```java
private static final int MAX_DEBRIS_BLOCKS = 192;   // ExplosionDebrisService
private static final int MAX_SHELL_BLOCKS  = 96;    // 单次爆炸的壳层
```

这道闸门防的是连锁爆炸：几十个 TNT 同时炸开，若每块都物理化，瞬间就是上万个刚体加两万个虚拟实体，服务器必然卡死。改成只接管弹坑外一圈之后，单发 TNT 的量级降到几十块。

## 每块单独成簇

结构坍塌里，簇是「一起掉下来的一整片」，做大一点既省虚拟实体又更像整体垮塌（默认 `cluster-grid-size: 4`，单簇最多 64 块）。

爆炸恰恰相反——要的就是**四散**。把相邻方块粘成 4×4×4 的块会让爆炸看起来像「几个大立方体被推开」，那是最不像爆炸的样子。所以飞溅路径下**一块一个刚体**。

代价是虚拟实体数：每块 2 个（1 个根实体 + 1 个 block display）。

## 快照盒的取法

碎块只能撞到快照范围内的碰撞体，所以盒子不能贴着碎块切：

```
水平方向  向外扩 3 格   —— 否则碎块生成瞬间周围全空，会直接穿过旁边没被炸到的墙
向上      扩 3 格
向下      扩 12 格      —— 碎块要沿真实地形落，脚下没有碰撞体就会穿地
```

盒子会被世界高度裁剪（`getMinHeight()` / `getMaxHeight()`）。

## 悬空清理

壳层处理「弹坑边缘那一圈」；结构分析只认「整体失联」的簇。两者之间还夹着一档：

**下方被本次爆炸炸空、但侧面还连着墙壁的方块** —— 结构分析以「连通到锚定」为支撑判据，它连到侧面墙壁所以判「仍有支撑」不塌，视觉上悬空。

`clearSuspended` 补这一档：从「本次爆炸腾空的位置」（弹坑 + 真正被掀走的壳层）出发做 BFS，**逐层向上传播** —— 凡正下方是已腾空位置的实心方块，判定「失去支撑」，物理化飞起，并加入下一轮传播（二楼的楼板被炸掉，三楼楼板也会跟着塌）。

关键设计：

- **只用「下方被本次爆炸移除」判定**，不碰「下方本来就是空气」的正常楼板/屋顶 —— 不会把一栋完好的房子拆了
- **传播限制在清理半径（威力 + 3）内、最多 8 层**，爆炸不至于抽空半个世界
- 未接管的直接移除为空气 —— 宁可少飞几块，也不能让方块悬空
- 与坍塌分析同 tick 衔接：悬空清理处理「局部下方空」，坍塌分析处理「整体失联」，两档互补

## 为什么在 MONITOR 优先级上读事件

我们现在**不修改** `blockList()`，但仍然要在 MONITOR 上读它：

- 放在 MONITOR **之前**（如 HIGH）读，拿到的是还没被保护插件过滤的名单。WorldGuard 之类通常在 HIGHEST 把领地内的方块从 `blockList()` 里摘掉——照那份名单去算壳层，等于把别人领地边上的方块炸飞。
- 放在 MONITOR 读，拿到的是所有插件处理完的**最终名单**，保护规则天然被尊重。

## 冲量

复用 `CollapseImpulse.ofExplosion(x, y, z, power)`：

- 半径 = `max(4, power × 2)`，与原版爆炸的破坏半径同比例，让「被炸飞的范围」与「被炸碎的范围」在观感上对得上
- 衰减是**线性**的 `1 - d/r`，不是平方反比——平方反比在爆心附近会把最近的碎块以夸张的速度弹射出去，看起来像 bug 而不像爆炸

### 贴地爆炸把冲量原点沉下去

纯径向冲量在贴地爆炸时有个问题：弹坑边缘那一圈与爆心几乎等高，径向方向近乎水平——方块贴着地面滑出去，像被扫堂腿放倒，完全不是「炸起来」的样子。

因此贴地时把冲量原点沉到爆心之下 `EJECTA_ORIGIN_DROP = 1.5` 格。同一条径向方向自然带上仰角，边缘方块变成**向上向外喷**，这正是真实弹坑抛射物的形状——而且不必在施力那边再加一路特殊的竖直分量。

对外事件 `ExplosionDebrisLaunchEvent` 报的仍是**真实爆心**，沉下去的只是冲量原点。

### 威力推断

`EntityExplodeEvent` 不暴露威力值（`getYield()` 是掉落率不是威力），只能按爆炸源类型取原版经验值：

| 来源 | 威力 |
|---|---|
| TNT / TNT_MINECART | 4.0 |
| 苦力怕 | 3.0（闪电苦力怕 6.0） |
| 末影水晶 | 6.0 |
| 凋灵头颅 / 火球 | 1.0 |
| 其它 | 3.0 |

## 碎块落地之后

走与结构坍塌完全相同的落地链路：

- 脆性方块（玻璃、树叶）按 `fracture-speed` 判定破碎，见[材质系统](materials.md)
- 其余按 `settle.yml` 的区域规则写回真方块 / 掉落物 / 消失
- 掉出世界底部的直接销毁，不写方块也不掉落

因此「TNT 把玻璃掀飞 → 玻璃落地摔碎 → 什么都不掉」这条链是自然成立的，不需要额外特判。

---

## 关闭

`systems.yml` 的 `systems.debris: false` 关掉整套冲击波飞溅（含悬空清理），爆炸退回纯原版行为。

也可以把该世界加进 `config.yml` 的 `disabled-worlds`——整套物理托管都会跳过它。
