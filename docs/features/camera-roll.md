# 视角滚转系统

## 概述

GTRigidPhysics 的视角滚转系统让玩家在爆炸、坍塌、碎块翻滚时感受到画面倾斜——尽管原版 Minecraft 协议中根本没有"让客户端把画面转个角度"这种包。这里的做法是：服务端把角度编码进一颗粒子的颜色，由随插件分发的**资源包着色器**在客户端解码并旋转整个画面。

参考：DESIGN.md 未设独立章节，代码分布在 `common/shader` 和 `paper/shader` 包下。

---

## 为什么视角滚转要靠一颗粒子来传

原版协议里没有摄像机 roll 的控制通道。着色器唯一能读到的、由服务端控制的逐帧数据，就是屏幕上像素的颜色。

因此整个方案是：

1. 服务端发一颗颜色被精确编码过的 `ENTITY_EFFECT` 粒子，位置取玩家脚下（紧贴摄像机，保证一定在视锥内）
2. 资源包覆盖 `core/particle.vsh` 着色器，认出"数据粒子"，把它画到屏幕角落一个约定像素上
3. 后处理管线（`core/positional_color.fsh` 等）从那个像素解码出角度，旋转整个画面

粒子在这里不是特效，而是一根**单向数据线**。

---

## 前置条件

**视角滚转必须配合资源包才有效果**，且客户端需要满足：

1. 开启"Improved Transparency"（旧称"Fabulous! / 华丽"）画质选项——**最常见的失效原因**。这个选项控制核心着色器（`core/` 目录）是否被加载，关闭后粒子着色器不会被调用
2. 没有加载 Iris 光影包。光影包会用自己的管线接管整个渲染，让资源包着色器被整体忽略
3. Sodium 版本 >= 0.9.0（26.2 对应版本线）。更早版本有一个粒子着色器 uniform 归零的 bug，导致着色器读到的角度永远是 0

## 版本兼容

### 26.2（已适配，2026-08-06）

26.2 引入了**反向深度缓冲**（near=1、far=0），旧实现里 marker 四边形用 `gl_Position.z = 0.0`，
在反向深度下几乎是最远，永远过不了深度测试——整条管线**静默失效**：着色器照常编译、
日志一切正常，但 marker 从不落笔，画面永不滚转。同时 26.1 起的原版 `particle.vsh` 已把
光照贴图采样从 `texelFetch(Sampler2, UV2 / 16, 0)` 换成 `sample_lightmap(Sampler2, UV2)`。

修复动作（对齐上游 ShaderSelectorV4 的 `26.2` tag，该 tag 已实测）：

| 位置 | 改动 |
|---|---|
| `core/particle.vsh` | import：`minecraft:globals.glsl` → `minecraft:sample_lightmap.glsl` |
| `core/particle.vsh` | marker 四边形 `z = 0.0` → `1.0`（反向深度下为最近，必过深度测试） |
| `core/particle.vsh` | 光照贴图：`texelFetch(Sampler2, UV2 / 16, 0)` → `sample_lightmap(Sampler2, UV2)` |
| `pack.mcmeta` | 补 `pack_format: 88`，保留 `min_format 88` / `max_format 9999` |
| `assets/sodium/` | 整目录删除（Sodium 0.9.x 迁移到 Blaze3D，旧覆盖会污染区块渲染） |

其余文件（`particle.fsh`、`post_effect/transparency.json`、`data.fsh`、
`marker_settings.glsl`）经 26.1.2 与 26.2 客户端 jar 逐字节比对，确认在 26.2 上有效，
无需改动。编码端 `ShaderRollProtocol`（G=251 立刻设定 / G=252 最短弧插值）与上游
`data.fsh` 的 op 0–4 语义一致，同样不动。

### 26.3（风险，跟踪中）

Mojang 在 26.3-snapshot-2 移除了 `post_effect/transparency.json` 后处理链（半透明改用引擎端
OIT 合成），`minecraft:particles` 帧缓冲目标随之消失；26.3-snapshot-5 起着色器改由 ShaderC
编译、`#moj_import` 换成 `#include`、in/out 需显式声明 location。本系统的两个挂钩点
（transparency 链注入 + 粒子缓冲数据通道）在 26.3 双双作废，纯资源包全屏旋转能否存活存疑。

当前策略：跟踪上游 ShaderSelectorV4 的 `end_of_frame` + OIT 移植，验证 `end_of_frame`
扩展点是否足够承载全屏旋转；若不可行，转向无着色器兜底（受击倾斜动画）或客户端 mod 路线。

### 前向兼容原则

本项目只向上更新。`pack.mcmeta` 的 `max_format: 9999` 保证未来客户端**接受**本包而不会
拒收——但「接受」不等于「生效」，每个大版本都要按上表逐项核对一次。

## 精度限制

协议只有 **8 位角度**，即 256 个刻度均分 360°，每刻度 **1.40625°**。

- 比这更小的角度变化在线路上无法表达——差异小于 1.4° 的两个角度会编码成完全相同的字节
- 这是协议的硬上限，不是本系统的实现取舍
- 好在它远低于人眼对画面倾斜的感知阈值（约 5~10°），做震动和倾斜都够用
- 精度限制也是发包节流的基础：稳态下绝大多数 tick 的角度变化都在 1.4° 以内，这些包被跳过，节省了大量流量

---

## 四种字节的分工

一颗粒子的 ARGB 四个字节分别承担不同角色：

| 通道 | 值 | 含义 |
|---|---|---|
| A（Alpha） | 251 | 校验位之一 |
| R（Red） | 254 | marker 标志，着色器靠它区分"数据粒子"与普通粒子 |
| G（Green） | 251 或 252 | 操作码：251 = 立刻设定，252 = 最短弧插值 |
| B（Blue） | 0~255 | 角度值本身 |

用 A 和 R **两个字节**做校验而不是一个，是因为普通粒子的颜色是玩家可见的：单字节校验意味着任何一颗恰好红到 254 的粒子都会被误认成数据粒子，让画面莫名其妙地歪掉。两个字节把误判概率压到可以忽略。

### 两种操作码

| 操作码 | Green 值 | 含义 | 使用场景 |
|---|---|---|---|
| 立刻设定 | 251 | 画面下一帧就跳到目标角度 | 震动（逐 tick 变化，防止客户端插值追不上） |
| 最短弧插值 | 252 | 着色器以固定角速度转向目标 | 回正、一次性目标角 |

#### 瞬时模式下"立刻"是真的吗

严格说是"客户端下一帧"，即 50 ms 以内。对震动的 2~3 Hz 频率来说，这已经是瞬时了。

必须用瞬时模式是因为：震动逐 tick 变，插值模式下客户端以固定角速度慢慢追一个每 tick 都在变化的目标，永远追不上——表现为震动被抹平成一个迟钝的缓慢漂移。

#### 刻度量化差异

瞬时模式按 255 刻度量化（`b/255`），插值模式按 256 刻度量化（`b/256`）。不一致是**刻意的**：

- 插值模式是循环的——着色器里 `1.0 = 0.0`。若也按 255 量化，`255/255 = 1.0` 就与 `0/255 = 0.0` 撞在一起，白白浪费一个刻度
- 瞬时模式不是循环的——角度值直接设定，不需要考虑首尾重合

## 三种震感来源

### 1. 爆炸冲击

爆炸瞬间猛地滚一下，然后震荡回正。

关键参数：

| 参数 | 默认值 | 含义 |
|---|---|---|
| degrees | 14.0 | 爆心处的初始振幅，再按爆炸威力开方缩放 |
| radius | 20.0 | 影响半径（格），也按威力缩放 |
| frequency | 2.4 Hz | 震荡频率，接近真实爆炸冲击后的晃动节奏 |
| decay | 0.7 s | 衰减时间常数，约 2 秒后彻底消失 |

**威力对振幅的影响开方而非线性**：原版威力 1（火球）到 6（充能苦力怕）是 6 倍差距，线性放大会让充能苦力怕直接把画面顶到上限——而那本该是留给"贴脸挨了一发"的表现空间。开方后 1 对 6 的振幅差约 2.45 倍，画面表现分层合理。

**震荡方向**取决于震源在玩家的左侧还是右侧。在爆炸那一瞬间定死，之后玩家转身也不改——冲击波不会跟着人转。

### 2. 大型坍塌震感（不自动触发）

持续而轻微的摇晃，与爆炸冲击的"尖锐"形成对比。

!!! warning "坍塌链路不会自动调它"
    引擎内部已经摘掉了「坍塌 → 震屏」这条自动连线。碎块本身与落地音效就是坍塌的表现，
    再叠一层画面滚转既不还原（塌一堵墙不该让十米外的人天旋地转），又会与爆炸的震感混淆
    —— 玩家分不清刚才是炸了还是塌了。

    本节配的是**显式调用**那条路径：对外 API 的 `CameraEffectService#collapseAt`，
    以及命令与面板的自测入口。想让坍塌自动震屏，在自己的插件里监听
    `StructureCollapseStartEvent` 再调 `collapseAt` 即可。

关键参数：

| 参数 | 默认值 | 含义 |
|---|---|---|
| degrees | 6.0 | 基准振幅，远小于爆炸——避免整场坍塌一直在晕 |
| radius | 40.0 | 比爆炸大得多：一栋楼塌下来，隔着几十格也该感觉到 |
| frequency | 1.1 Hz | "沉重的晃动"而非"尖锐的冲击" |
| decay | 1.6 s | 衰减时间，余震拖得更久 |
| min-blocks | 40 | 低于这个方块数的坍塌完全不产生震感 |
| full-blocks | 400 | 达到这个方块数即为满幅，超过不再增强 |

规模换算公式：

```java
if (blockCount <= minBlocks) return 0.0;       // 拆两格墙不该晃
if (blockCount >= fullBlocks) return 1.0;       // 再大也没区别了
return (blockCount - minBlocks) / (fullBlocks - minBlocks);  // 线性插值
```

没有 `fullBlocks` 上限的话，一次上万方块的坍塌会把倍率推到荒谬的数值——而超过某个规模之后，再大的坍塌在观感上也没区别了。

### 3. 跟随碎块翻滚

画面跟着身边正在翻滚的巨块一起歪。

#### "骑乘"的真实含义

碎块是 **packet 虚拟实体**，服务端根本不存在这些实体，玩家不可能真的骑上去，也不会被它们托住。所以这里做的是空间上的**近邻判定**：玩家身边（`followRadius` 默认 3.5 格）若有正在翻滚的碎块，就让画面跟着**最近那一个**的姿态歪。

观感上这是对的——站在正在垮塌的废墟里，天旋地转本来就该来自身边翻滚的巨块，而不是"我坐在某个特定方块上"。

#### 姿态投影

同一个歪倒的碎块，玩家正面看是左右歪，侧面看则是前后倾——而屏幕滚转只能表达左右歪。所以不能直接取刚体的 roll 欧拉角（那是相对世界轴的），必须把它投影到玩家当前的右方向上：

```java
// 旋转矩阵的第二列 = 局部 +Y 轴转到世界坐标后的方向
double upX = 2.0 * (x * y - w * z);
double upY = 1.0 - 2.0 * (x * x + z * z);
double upZ = 2.0 * (y * z + w * x);

// 玩家右方向（水平面内）
double rightX = -Math.cos(yaw);
double rightZ = -Math.sin(yaw);

// 上方向在「玩家右侧」与「世界竖直」两个轴上的分量之比
double lateral = upX * rightX + upZ * rightZ;
return Math.toDegrees(Math.atan2(lateral, upY));
```

用 `atan2` 而非 `asin`：碎块可能翻过头（up 朝下），`atan2` 能正确表达整个 +-180 度，`asin` 会在超过 90 度时把角度折回来，表现为碎块翻过顶点后画面突然回摆。

#### 关键参数

| 参数 | 默认值 | 含义 |
|---|---|---|
| followRadius | 3.5 | 多近才跟随，不建议超过 6——会让人在废墟区域持续眩晕 |
| followStrength | 0.75 | 跟随强度，1.0 = 完全复制碎块姿态 |
| followInvert | false | 方向取反，**只有真机能确认** |

## CameraRollService 的核心设计

### 三种来源的叠加

协议只有一个 roll 通道。三种来源要是各发各的，后发的包就会直接覆盖先发的——爆炸震动会被坍塌震感抹掉，谁最后发谁赢。因此叠加必须在服务端算完再发。

叠加逻辑：
- **爆炸冲击**和**坍塌震感**是震动——可以直接相加
- **跟随碎块翻滚**是姿态——一个绝对角度

三者求和后统一截断到 `maxDegrees`（默认 25 度）。截断是必需的：连炸几发时若不设上限，画面会转成风车。

### 稳态零开销

没有震动、也没有进行中的坍塌时，`tick()` 第一行就返回。整套机制在稳态下是零开销——这很重要，因为它跑在 **每 tick**。

### 每 tick 调用而非跟着位姿广播走

震动频率在 2~3 Hz，按采样定理至少要 6 Hz 才不失真。跟着位姿广播走 2~4 tick 一次（5 Hz）的话，采样率低于信号频率，震荡会混叠成一个缓慢的漂移——看起来就是画面在莫名其妙地慢慢歪来歪去。

### 单个玩家最多叠加 4 个震动源

这不是性能考虑（一次求值就几个浮点乘法），而是**观感**考虑：连炸十发时十个震动叠加会把画面搅成高频抖动，只会让人恶心。超出后丢弃最老的那个——最老的也一定是衰减得最厉害的。

## 发包节流

精度只有 1.40625 度/刻度。差异小于一个刻度的两个角度会编码成同一个字节，发出去的是一模一样的包。

`ShaderRollChannel` 记住每个玩家最后发出去的角度（`Map<UUID, Double>`），差异不可区分就跳过。这类包在稳态下占绝对多数（震动已衰减完、碎块已静止），不拦掉就是每玩家每秒 20 个纯废包。

### 节流的代价

必须在客户端状态可能被重置的时机主动 **forget**：

| 时机 | 原因 |
|---|---|
| 资源包重载 | 着色器数据纹理被重建成全 0 |
| 玩家重进世界 | 渲染状态重建 |
| 玩家死亡重生 | 同上，且顶着歪掉画面复活体验极糟 |
| 玩家换世界 | 同上 |
| 玩家退出 | 清理内存，防止 map 无限增长 |

忘记这一步的话：客户端已回到水平、服务端却还记着"上次发的是 30 度"，接下来每一 tick 都判定"值没变，不用发"——玩家的视角滚转**永久失效**，而日志里一切正常。

---

## 回正的特殊处理

回正是唯一一个"目标固定、过程可以交给客户端"的动作。走插值模式（而非瞬时模式），让着色器自己以固定角速度转回水平——比服务端逐 tick 喂中间值节省 20 倍的包。

## 资源包下发流程

原版协议只接受一个 URL，客户端自己去下载。服务端没法把文件直接推给它。

### 流程

1. `./gradlew build` 产出 `build/distributions/GTRigidPhysics-RP-<版本>.zip` 并打印其 SHA-1
2. 把 zip 传到自己的对象存储 / CDN / 静态站，拿到**直链**（必须是直接下载地址，网盘分享页的 HTML 链接不行）
3. 把直链和 SHA-1 填到 `config.yml` 的 `resource-pack` 段，`enabled` 改 true

### SHA-1 是缓存键

客户端用 SHA-1 判断"资源包是否已下载过"。填对了玩家只在资源包真正的变了时才重新下载（几 MB）；填错或留空会导致**每次进服都重新下载**。

因此本插件在 SHA-1 不合法时**拒绝下发**并在日志说明原因，而不是"不带 hash 照发"——后者能用但很慢，属于最难被发现的那类故障。

## 怎么自测客户端

让画面做一个小幅度的来回滚转，就能立即验证客户端那一半是否装好：

- 画面没有滚转 → 着色器未加载（检查 Improved Transparency 与 Iris）
- 画面滚转了但幅度不对 → Sodium 版本可能太老
- 画面滚转了且幅度正确 → 一切正常

!!! warning "`/gtrp shader test` 已经不在引擎里"
    引擎瘦身把 shader 命令一起迁出了。现在的入口有两个：

    - [管理面板 addon](../addons/panel.md) 的「视角效果」页
    - 自己的插件里调 `api.cameraEffects()`

    「画面歪着停不下来」时的紧急回正同理 —— 面板上有对应按钮。

!!! info "本系统按设计应当整体迁出为 addon"
    `shader` 包（视角滚转 + 资源包下发）涉及资源包强制下发，不宜内置于引擎，
    规划中要迁成「视觉体验材质包」addon。

    **这一步尚未完成** —— 效果本身目前仍由引擎提供。

## 降级兜底：没有着色器时的受击倾斜

平滑滚转依赖资源包着色器，而它在很多情况下会**静默失效**：服务端没配置资源包、
玩家拒绝或下载失败、客户端没开 Improved Transparency、装了 Iris、
或未来版本移除了着色器挂载点。此时粒子照发、日志正常，但画面纹丝不动。

`fallback` 配置让系统在这种时候改用**原版受击倾斜动画**（`hurt_animation`）
兜住爆炸冲击与坍塌开场——它是原版唯一无需着色器、服务端可控方向的「画面歪一下」。

- **能力边界**：幅度固定（客户端算的）、约 0.5 秒自动衰减、自带一小段受击红色渐变。
  表达不了平滑滚转，也承接不了「跟随碎块翻滚」。
- **方向**：震源在玩家左/右侧 → `hurtDir = ±90°`，与着色器路径的横向投影语义一致；
  `fallback.invert` 用于真机纠偏。
- **门控**：`fallback.min-degrees`（默认 4°）只对「本该有至少这么多度滚转」的震动兜底；
  `HurtShakeFallback` 内还有 8 tick 的节流，防止连炸时动画被反复重开。
- **AUTO 的判定**：服务端没配置资源包 → 一律兜底；配置了则看该玩家的
  `PlayerResourcePackStatusEvent`，加载失败/拒绝即兜底。客户端渲染设置
  （Improved Transparency、Iris）服务端无法观察——加载成功只是「有希望」，
  不保证真的生效；确知失效时服主应改 `fallback: hurt` 强制兜底。

## 使用边界与注意事项

- **没有资源包就绝对没有效果**。服务端只发粒子，没有着色器解码的话画面完全不受影响。
- **Improved Transparency 是开关**。关闭后核心着色器（`core/` 目录）不会被加载，是整个系统最常见的失效原因。
- **Iris 光影与着色器互斥**。光影包会用自己的管线接管渲染，让资源包着色器被整体忽略。
- **精度上限 1.4 度**。比这更小的数值配了也没意义——在线路上根本无法表达。
- **节流依赖 forget**。忘了在 `ShaderStateListener` 中注册新的重置时机，会导致客户端状态与服务端记忆不同步——"功能莫名其妙消失了"。
- **回正必须走插值模式**。瞬时回正画面会硬跳，观感差且浪费带宽。
- **`followInvert` 只有真机能确认**。左右方向取决于着色器实现细节和屏幕坐标系约定，开发环境无法测试。
- **SHA-1 必须填写**。不是可选的完整性校验，是客户端缓存键。不填写会导致玩家每次进服重下几 MB。
