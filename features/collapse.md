# 结构分析系统

## 概述

GTRigidPhysics 的结构分析系统是判断"建筑是否该塌下来"的核心算法。它在方块破坏事件后异步运行，通过锚定 flood fill 找出与地基失去连接的所有连通分量，再按体积上限切成碎块簇。分析跑在异步线程上，对主线程几乎无感——典型爆炸区域（32 立方）约 2.6 ms。

参考：DESIGN.md 12.2、12.3、17.3。

---

## 核心算法：锚定 flood fill + 失联切簇

### 两趟线性扫描，整体 O(n)

**第一趟：支撑标记。**
以所有"锚定"方块为种子做 BFS flood fill，凡是能从锚定点到达的实心方块都标记为"已支撑"。

**第二趟：失联收集。**
遍历剩余未被支撑的实心方块，对每一个未访问的格子做连通分量划分。每个连通分量就是一个坍塌簇。

### 伪码

```
markSupported(snapshot, settings):
    收集所有锚定格子 → 栈
    while（栈非空）:
        弹出 → 标记 supported
        遍历邻域 → 实心且未标记的进栈

collectDetached(snapshot, supported, settings):
    for each（未支撑的实心方格）:
        在新的网格单元内做 flood fill
        到达单元边界或方块数上限时停止
        产出 DetachedCluster
```

参考：DESIGN.md 5.2、12。

## 18 邻域 vs 6 邻域

### 为什么默认 18 邻域

只认六个面（`FACE_ONLY`）在几何上最"干净"，但对**建筑**是错的：楼梯、斜撑、错缝砌法、对角搭接在真实建筑里极其常见，这些结构**仅靠棱相连**。只认面会把它们判成"已经断开"——房子还立着就先塌了一半。

另一头的 `FULL_26`（含体对角）则太松：只共用一个顶点的两个方块在物理上几乎不传递载荷，认它相连会让本该塌的结构赖着不塌。

所以默认取中间的 `FACE_AND_EDGE`（18 邻域 = 6 面 + 12 棱）。这不是拍脑袋——该领域最成功的开源物理实现（Sable / Simulated）在四处独立的连通性算法里用的都是同一套 18 邻域，是经过大规模实战验证的默认值。

### 三种模式对比

| 模式 | 邻居数 | 适用范围 | 性能（32 立方） | 性能（64 立方） |
|---|---|---|---|---|
| `FACE_ONLY` | 6 | 最严格，可能多塌 | 1.16 ms | 8.24 ms |
| `FACE_AND_EDGE` | 18 | **默认**，兼顾正确性与性能 | 2.65 ms | 22.5 ms |
| `FULL_26` | 26 | 最宽松、最不容易误塌，代价是也最不容易塌 | 比 18 邻域略慢 | 比 18 邻域略慢 |

### 生成偏移表

曼哈顿距离恰好把三类邻居分开：

```
|dx|+|dy|+|dz| = 1 → 面（6 个）
|dx|+|dy|+|dz| = 2 → 棱（12 个）
|dx|+|dy|+|dz| = 3 → 体对角（8 个）
```

只含体对角时不包含面的重复，所以 `FACE_AND_EDGE` 的偏移数就是 6 + 12 = 18 个三元组，共 54 个 int。

## 空间网格切分策略

### 单簇体积上限：64 方块

通过把 flood fill 限制在 `grid³` 的空间网格单元内实现（默认 grid=4，上限 4³=64）：

| 参数 | 值 | 权衡 |
|---|---|---|
| 太大 | 256+ | 旋转时 transformation 更新量爆炸；大块整体倒下观感僵硬 |
| 太小 | 8 | 刚体数量上升、失去"整块墙倒下"的结构感 |
| 当前 | 64 | 初始值，需实测调 |

### 网格切分的三个好处

1. **簇大小天然有上限**，无需事后切割
2. **簇形状是块状的**，倒下来像真实碎块，而非 BFS 层序产生的怪异条带
3. **同一网格单元内的多段独立结构**（例如两根柱子穿过同一格）会被正确地分成多个簇，而不是错误地粘成一个

## 边界策略：侧面+底面锚定、顶面不锚定

快照是有限区域，如何对待区域边界直接决定算法是"保守"还是"疯狂"。

| 边界 | 策略 | 原因 |
|---|---|---|
| 侧面（±X、±Z） | **锚定** | 区域外的结构可能仍连着地基，没有证据表明会塌 |
| 底面（Y=0） | **锚定** | 下方式块可能连到 bedrock |
| 顶面（Y=max） | **不锚定** | 重力向下，上方方块不提供支撑 |

此外，世界 Y 低于 `anchorBelowY` 的方块也视为地基——这是"地下岩层"的语义。

### 代价

取侧面锚定的代价是：**快照区域必须足够大**以覆盖整个可能坍塌的结构。区域取小了，结果是"几乎不塌"（所有东西都连到侧面边界），而不是报错。这是一种保守失败，可接受。

## 事件时机：BlockBreakEvent 延迟 1 tick

`BlockBreakEvent` 触发时方块**尚未真正从世界移除**。此刻抓快照会读到旧状态——方块还在原地，结构仍完整，分析结果自然是"什么都没断"。

因此触发监听器在收到事件后，用 `runTask` 延迟 **1 tick** 再发起判定：

```java
plugin.getServer().getScheduler().runTask(plugin,
    () -> service.requestCollapseCheck(location, ...));
```

1 tick 后，被破坏的方块已从世界消失，快照反映的才是"破坏后"的真实状态。

## 异步窗口复核

结构分析跑在异步线程上（快照解析 + flood fill），但分析期间世界可能被其他玩家改动。

因此落地时必须逐块复核"当前方块是否仍与快照一致"：

```java
// 复核：异步窗口内世界可能已变
if (!block.getBlockData().equals(expected)) {
    return;   // 跳过，避免凭空造方块或拆掉别人刚放下的建筑
}
```

不一致就跳过——宁可少写，不可错写。

## 性能基线

| 边长 | 体积 | FACE_ONLY | FACE_AND_EDGE |
|---|---|---|---|
| 16 | 4,096 | 0.082 ms | — |
| 32 | 32,768 | 1.157 ms | **2.645 ms** |
| 48 | 110,592 | 3.466 ms | — |
| 64 | 262,144 | 8.241 ms | **22.5 ms** |

单格均摊稳定（~0.000031 ms/格），完美线性。典型爆炸区域（32 立方）约 2.6 ms，跑在异步线程上完全可接受。只有把 `analysis.radius-xz` 开得很大时才需要考虑降级到 `FACE_ONLY`。

## 触发监听器的廉价预筛

玩家挖矿会高频触发 `BlockBreakEvent`。全量分析虽然只要几毫秒，但每挖一格都跑一次纯属浪费。

因此触发监听器先做一步**极廉价的预筛**：

```java
private boolean mayAffectSupport(Block block) {
    if (!isFree(block.getRelative(BlockFace.UP))) return true;   // 最常见，先单独查
    for (int dx = -1; dx <= 1; dx++) {
        for (int dz = -1; dz <= 1; dz++) {
            if (dx == 0 && dz == 0) continue;
            // 斜上方：它压在被拆的这一格上
            if (!isFree(block.getRelative(dx, 1, dz))) return true;
            // 同层：只有**悬空**的邻居才可能靠这一格连回地基
            Block side = block.getRelative(dx, 0, dz);
            if (!isFree(side) && isFree(side.getRelative(BlockFace.DOWN))) return true;
        }
    }
    return false;
}
```

判据两句话：**上层 9 格任一实心**，或**同层 8 格里有实心且悬空的邻居**。

### 为什么不能只看正上方

从前这里只查一句 `getRelative(UP).isSolid()`。支撑传播用的却是 18 邻域——一格方块能撑住它**斜上方**的邻居，也能替**同层**的邻居把载荷送下去。于是最典型的两类拆法直接被预筛吞掉，压根不会触发分析：

- **拆水平梁 / 走廊 / 桥面**：被拆那格的正上方是天空，但梁的另一头就此彻底悬空；
- **拆悬挑的根部**：支撑柱顶那格上面已经没东西了，靠它挑出去的一整片却全靠这一格连回地基。

玩家看到的现象正是「拆断了没反应，再往旁边多拆几格才忽然全塌」——那几格里总有一格上方压着东西，于是替前面几次补上了那一次分析。

### 同层邻居为什么要再加「悬空」这一条

光看「同层有实心邻居」会把**平地挖一格土**也放行——四周都是土，而那种破坏绝不可能引起坍塌。区别在于邻居**脚下有没有东西**：

| 邻居正下方 | 含义 | 处理 |
|---|---|---|
| 实心 | 它自己站在更低的地基上，横向少一个伙伴无关紧要（平地、地表、山体内部） | 跳过 |
| 空的 | 它**靠横向连接活着**，被拆的这一格很可能正是它通往地基的唯一通路（水平梁、桥面、悬挑） | 分析 |

加上这一条之后，判据既捕获了上面那两类漏判，又不让日常挖土多花一次分析。

**下层刻意不看**：支撑自下向上传播，拆掉一格只有它上方与同层的邻居可能失去通路。下方的方块要么本来就站在更低的地基上，要么是倒 U 形吊挂结构——后者极罕见，且会在下一次破坏时被捕获，不值得为它把每次挖土都变成一次全量分析。

预筛仍然是**保守**的：会放过一些实际不塌的情况（挖矿时上方是连片山体），那些在正式分析里会被判成"仍有支撑"，只多花几毫秒。

## 区块级冷却与挂起补跑

同一区块两次分析之间至少间隔 **500 毫秒**（可配置）。防止玩家连续挖矿在同一小片区域高频触发重复分析。

冷却用 `Map<Long, Long>` 在内存中维护，并在条目超过 4096 时自动清理过期项。

### 被挡下的请求不会被丢掉

冷却与并发上限都是**限流**，本意是"别重复算"，不是"这次判定不重要"。但玩家连续拆方块时，**拆断的那一下**完全可能正好落在冷却窗口里——静默丢弃它，结构就一直悬在那儿，直到下一次破坏碰巧越过冷却才忽然全塌。这是「拆断了却不塌」的另一半原因。

所以挡下的请求会**挂起**，冷却到期后自动补跑一次：

| 挡下的原因 | 补跑间隔 | 备注 |
|---|---|---|
| 区块冷却 | 剩余冷却 + 1 tick | 差一毫秒就又被挡回去，白绕一轮 |
| 并发上限 | 5 tick | "此刻正忙"，几 tick 后就有空位 |

同一区块只保留**最后**一次请求（分析范围高度重叠，跑最新那次即可），补跑任务也只在第一次挂起时排——否则连续拆二十格会排出二十个任务。两道量的保护：单个请求最多补跑 4 回、挂起队列最多 64 个区块。

`/gtrp status` 的「结构分析」一行会显示 `运行中 / 挂起` 两个数，两个一起看才知道系统是"刚好够用"还是"已经追不上了"。

## 自适应扩范围：答案受边界限制时放大重算

侧面锚定的代价（见上文）不只是"要把区域开大"，而是**它无法从结果里看出来**：一座横跨边界的建筑哪怕在区域内彻底断开，也会因为另一头搭在边界上而被判"仍有支撑"，而分析本身报的是一个干干净净的"没有坍塌"。

`AnalysisResult.borderLimited()` 把这件事变成可检出的信号：把侧面锚定关掉再跑一趟支撑标记，两次的差集就是「只靠边界活下来的方块」。

```java
boolean[] withBorder    = markSupported(snapshot, settings, failed);
boolean[] withoutBorder = markSupported(snapshot, settings.withoutSideBoundaryAnchor(), failed);
borderRescued = count(i -> withBorder[i] && !withoutBorder[i]);
```

- **差集为空** → 所有支撑都落在区域内的真实地基上，放大一万倍结论也一样，不必多算；
- **差集非空** → 自动把水平半径 ×2 重抓快照再算一次（最多 `border-expansion-passes` 趟，上限 `max-radius-xz`）。

### 为什么这个判据不会误报地面

地面靠的是 `anchorAtBottom`（快照底面，默认在脚下 32 格）与 `anchorBelowY`，两者都不受侧面锚定影响。关掉侧面锚定后，地表仍能通过土石一路连到快照底面。真正只靠侧面活着的，恰恰就是从区域侧面伸出去的悬挑、长桥、贴边墙体——也正是要检出的那些。

### 开销与保护

放大重算是「多花一趟换准确」的**可选品**，因此：

- 只在 `borderLimited()` 为真时才跑，绝大多数拆迁（房屋、柱子、小桥）一趟都不多花；
- 并发上限**压到 1**，不与正常判定抢分析线程。没有这一条，森林大火 / 连锁爆炸场景下每个受灾区块都会排出两三趟半径 48 的全量分析（体积是基准的 16 倍）；
- 抢不到配额的直接放弃、不进挂起队列——下一次破坏还会重新触发。

配置：`analysis.yml` 的 `border-expansion-passes`（默认 2，0 = 关闭）与 `max-radius-xz`（默认 48）。

## 触发面：结构不在乎是谁把那一格拿走的

除了 `BlockBreakEvent` 与 `EntityExplodeEvent`，下面这些同样会让结构失去支撑，因此都接上了同一条判定管线：

| 事件 | 场景 | 预筛 |
|---|---|---|
| `BlockExplodeEvent` | 错误维度里的床与重生锚（爆炸源是方块本身，**不是** EntityExplode） | 走完整的爆炸路径：镜头冲击 → 冲击波飞溅 → 悬空清理 → 结构判定 |
| `BlockPistonExtendEvent` / `RetractEvent` | 活塞抽走承重柱 | **专门的**判据：被移动的方块里有哪一格正压着别的东西，且压着的那格不在同一摞里。通用预筛会放行每一台红石钟 |
| `BlockBurnEvent` | 火烧断横梁（木结构最常见的失稳方式） | 通用预筛 |
| `BlockFadeEvent` | 冰雪融化、珊瑚死亡 | 通用预筛 |
| `LeavesDecayEvent` | 树屋、藤桥失去托底 | 通用预筛 |
| `EntityChangeBlockEvent` | 末影人搬走一格、凋灵撞碎一片 | 额外要求 `getTo()` **非实心**——否则羊群啃草皮（草→泥土）足以把分析管线占满 |

这些触发在事件里带的起因是 `Cause.BLOCK_REMOVED`，与玩家亲手挖的 `BLOCK_BREAK` 分开：反作弊与日志通常只关心后者，而红石机械引发的坍塌往往要单独限流。

## 使用边界与注意事项

- **快照区域必须足够大**才能覆盖整个可能坍塌的结构。区域取小了，侧面锚定会让大部分结构被判为"仍连到外部"，结果是少塌而非报错。自适应扩范围（见上文）会在检出这种情况时自动放大重算，但它有并发配额，不能代替把 `radius-xz` 配到合理值。
- **BlockBreakEvent 必须延迟 1 tick**。立即抓快照读到的方块还在原地，分析不出断裂。
- **异步窗口复核不能省略**。否则会凭空造方块（把别人放的方块覆盖掉），或拆掉别人刚放下的建筑。
- **18 邻域的性能代价为 2~3 倍**（32 立方 2.6 ms vs 1.2 ms），买的是正确性。只在 `radius-xz` 开得很大时才需要考虑降级。
- **廉价预筛是保守的**：只有「上层全空 + 同层没有悬空的实心邻居」才跳过。**不要**把它退回"只看正上方"——那会漏掉拆水平梁与拆悬挑根部这两类最典型的拆法；也**不要**去掉同层那条「悬空」限制——那会让平地挖土每次都触发一次全量分析。
- **最坏情况（64 立方全失联）约 22.5 ms**。这不算"免费"，高频触发会累积。因此做了冷却（500 ms）和并发上限（默认 4）两道防护。
- **簇数上限是安全阀**。超出时会在日志 WARN 并留下部分悬空方块——这是刻意的：宁可告警也不静默丢弃。
