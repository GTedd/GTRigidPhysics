# 虚拟角色

> 源码：`physics/CharacterController.java`、`paper/object/PhysicsCharacter.java`

在物理世界中移动、被地形与刚体阻挡的「人形」实体。
一个由外部驱动的**轴对齐盒**，走「逐轴推进 + 就地退让」。

---

## 为什么不用通用引擎那种角色控制器

通用物理引擎提供的角色控制器（Jolt 的 `CharacterVirtual` 是典型）是为**任意几何的世界**设计的：
胶囊形状、斜面行走、自动爬台阶、可站立法线角……

代价是它与 Minecraft 的手感**处处对不上**。实测下来要补的洞包括：

- 没有摩擦
- 站在移动的物体上不会被带走
- 写回位置必须绕开服务端（服务端并不知道这个角色存在）

!!! success "干脆照原版实体的移动算法写"
    轴对齐盒、X / Y / Z **逐轴推进**、每轴各自被挡住就各自停下。

    这既是 Minecraft 玩家肌肉记忆里的手感，实现也简单得多 ——
    体素世界里逐轴推进本来就是**精确的**，不需要任何扫掠近似。

| 常量 | 值 | 说明 |
|---|---|---|
| `SLIDE_STEPS` | 3 | 一次移动最多分几段推进。段数越多，贴着墙走时越顺滑 |
| `GROUND_PROBE` | 0.08 格 | 判定「站在地上」的向下探测距离 |
| `STEP_HEIGHT` | 0.6 格 | 自动跨上台阶的最大高度。与原版玩家一致 |

## 它同时是「能推动物理方块」的落点

角色在引擎里注册为一个**运动学刚体**（`RigidBody.KINEMATIC`）：

- 求解器**不对它施加任何修正** —— 它的位姿由 `CharacterController` 驱动
- 但它会把碰到的动态刚体**推开**

于是「走进碎块堆里，把碎块踹开」不需要任何特判，是接触约束的自然结果。

!!! tip "推得动推不动是涌现的"
    小碎块被踢飞、大石块纹丝不动 —— 全部由质量与摩擦决定，没有一行判断代码。

## 角色 vs 刚体

| | 刚体（骰子 / 载具） | 虚拟角色 |
|---|---|---|
| `kind` | `DYNAMIC` | `KINEMATIC` |
| 谁决定它的位姿 | 求解器 | `CharacterController` |
| 被撞 | 会被撞飞 | 挡住不动 |
| 撞别人 | 会 | 会（这是它的主要用途之一） |
| 落地 | 自由落体 + 碰撞 | 贴地行走、自动爬 0.6 格台阶 |
| 渲染 | `BlockDisplay` 组 | 单个 `BlockDisplay` |

角色适合做「NPC 与物理世界交互」的底座：让 NPC 撞上骰子不会穿模，而是被挡住绕行。

## 重力由调用方施加

`CharacterController` **不自动施加重力** —— 它按当前的线性速度移动角色。

调用方（`PhysicsCharacter.update`）负责：

```
悬空时：垂直速度 += 重力 × dt   （下落）
着地时：垂直速度 = 0            （站住）
```

这个分工是刻意的：一个被脚本驱动的 NPC 可能需要飞、需要瞬移、需要无视重力，
把重力放在控制器里就得为每种情况开一个开关。

## 线程

角色刚体的创建走**命令队列排到物理线程的步进边界**（与所有刚体增删一致）。

API 调用先拿到句柄，角色在**下一物理帧**激活。这个一帧的延迟对调用方是透明的 ——
在它激活之前，`position()` 返回的是创建时给的初始值。

角色活在与独立物体**同一个** `ObjectPhysicsWorld` 里，所以角色能撞到骰子、载具、布娃娃。

## 预算

角色占用共享物理世界的刚体额度。`physics.yml` 的 `max-bodies` 里为它预留了 **64** 个：

```
独立物体             最多 256
布娃娃部件           最多 32 具 × 7 = 224
虚拟角色             最多 64
────────────────────────────
固定预留合计         544
地形流送             max-bodies − 544
```

默认 `max-bodies: 4096` 给地形留了约 3500 格的额度。详见 [`physics.yml`](../guide/config/physics.md)。
